🎯 The Goal of Phase 2

Phase 2 was all about creating the architecture and internal logic structure — not yet the user interface.

So you’re not worrying about forms or pages here.
You’re building the backbone — how the app handles data, business logic, and future scalability.

That’s why you have:

Models (data representation)

Repositories (data access layer)

Services (business logic)

Views (controllers for APIs)

Core (shared engine and configuration)



🧩 1. accounts App – Authentication and User Management

Purpose:
Handles user creation, login, roles (e.g., patient, doctor, researcher), and profile data.

Key Files:

models.py → Defines the User model extending AbstractUser to include roles and phone number.

repositories.py → Handles all database queries related to users (e.g., fetch user by email, create user).

services.py → Contains logic like registration, login validation, and role assignment.

views.py → Exposes endpoints (API or template-based) that call UserService.

urls.py → Maps endpoints to views.


Example flow:
User submits registration → UserService.register_user() validates and saves → UserRepository.create_user() commits to DB.

Why this matters:
It keeps authentication logic modular and reusable for future mobile integration.



💓 2. monitoring App – Vital Sign & Activity Tracking

Purpose:
Stores and processes sensor data (heart rate, respiratory rate, activity recognition).

Key Files:

models.py → Defines HealthRecord and ActivityRecord models with foreign keys to User.

repositories.py → Handles queries like “get user’s last 10 readings” or “save new health record”.

services.py → Contains data processing logic (e.g., average heart rate, detecting anomalies).

views.py → Exposes endpoints for submitting or retrieving health data.


Example flow:
Sensor data comes from frontend → HealthService.process_reading() cleans and stores → MonitoringRepository.save_record() commits it.

Why this matters:
All health-related logic stays in one module — easy to extend when adding new biosensors later.



🔄 3. sync App – Offline and Cloud Synchronization

Purpose:
Handles temporary offline storage (e.g., local caching) and cloud synchronization when connection returns.

Key Files:

models.py → Defines SyncLog (records sync attempts, timestamps, success/failure).

repositories.py → Manages sync logs and queued data.

services.py → Implements logic for detecting unsynced data and pushing/pulling it to/from server.

views.py → Provides API endpoints that frontend (PWA) can hit when coming back online.

Why this matters:
It makes the system “offline-first” ready, essential for remote users or unstable networks.



🔔 4. notifications App – Alerts and Reminders

Purpose:
Handles system notifications — reminders, abnormal readings, or periodic health check alerts.

Key Files:

models.py → Defines Notification model linked to User.

repositories.py → Handles queries like “get unread notifications”.

services.py → Manages logic for creating notifications (e.g., when heart rate > threshold).

views.py → Provides endpoints for marking notifications read or viewing them.

Why this matters:
You’re decoupling “event triggering” from “data management.”
Later, you can use Celery here for scheduled or background alerts.



📊 5. analytics App – Data Visualization & Insights

Purpose:
Handles analytics on collected data (averages, trends, insights, progress).

Key Files:

models.py → If needed, defines derived metrics or summaries.

repositories.py → Fetches aggregated data (using annotate, aggregate).

services.py → Business logic for insights (e.g., “average BPM per week”).

views.py → API endpoints serving data visualizations (for dashboards).

Why this matters:
You’ll plug these endpoints into Chart.js or similar on the frontend later.



🧠 6. core Directory – The System Brain

Purpose:
Contains reusable logic shared across the whole project.

Key Files:

config_loader.py → Implements Singleton Pattern.
It loads environment variables (API keys, Firebase configs) once and shares them across the project.

helpers.py → Shared utility functions like timestamp formatters, validators, etc.

constants.py → Stores global constants (e.g., role names, thresholds).

exceptions.py → Custom exceptions for cleaner error handling in services.

Why this matters:
Instead of repeating configurations and utilities across apps, you centralize them — improving maintainability.




🧩 How All These Pieces Interact

Here’s the big picture workflow:

Frontend → View → Service → Repository → Model → Database
                              ↓
                           Core Utils (Config, Exceptions, Constants)


Each layer has a clear responsibility:
✅ Views: Receive requests → delegate logic
✅ Services: Handle business rules, call repositories
✅ Repositories: Interact directly with DB
✅ Models: Define structure of data
✅ Core: Provides configuration, reusable tools
✅ Tests: Ensure each layer works independently

🧪 Why This Matters (for You as Developer)

This architecture gives you:

🔒 Clear separation of concerns (no tangled logic)

⚙️ Scalability (easy to add features)

🧱 Testability (you can test services/repositories independently)

🌍 Reusability (ideal for mobile integration later)

⚡ Performance-ready (suitable for Celery, caching, async tasks later)
